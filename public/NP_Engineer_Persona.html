The Engineering Builder

Everyone ships now — but the engineer ships for a living. This is the deep dive on who they are, what they need, and why winning them is the single most important motion for Amplitude's New Products in 2026.

The Key Distinction

Shipping Is the Job, Not Part of the Job

The frame that defines the entire engineering persona strategy

For the engineer, shipping code is the job. For everyone else, shipping code is increasingly part of the job — but not the whole job.

A PM who codes is still a PM. Their primary output is a spec, a decision, a strategy. Code is a means. A marketer who runs an A/B test is still a marketer. Their primary output is a campaign. The engineer's primary output is the code. Reliability, velocity, and correctness are the measurement.

When a PM uses feature flags, they want a dashboard that tells them the feature is working. When an engineer uses feature flags, they want an SDK that doesn't add latency, a reliable evaluation engine, an API they can script, and a rollback that takes 10 seconds. These are different products served by the same underlying infrastructure.

The Target

Who Is the Engineer? The Product Engineer.

The persona this strategy is built around is the product engineer — not the DevOps engineer, not the SRE, not the backend platform engineer. The product engineer owns a feature end-to-end: they write the feature, ship it behind a flag, run the experiment, and care whether users liked it.

They are the most tool-opinionated persona in any company. They choose their own stack, advocate for it internally, and resist tools that feel like they were designed by people who don't code. They are the fastest-growing budget owner in tech. As AI increases code throughput, the volume of flags, experiments, and releases is accelerating — and product engineers own all of it.

The Five Archetypes

Engineering Is Not One Persona — It's Five

Of the five archetypes below, the Product Engineer is the primary target. Every product decision, SDK investment, and GTM motion should be optimized for the product engineer first.

The Product Engineer

"I own the feature end-to-end — from spec to flag to experiment."

Works closely with PMs and designers but writes all the code. Uses feature flags to decouple deployment from release. Runs A/B tests on their own features, often without a data scientist. Daily Workflow

A Day in the Life of the Product Engineer

Understanding what the engineer actually does every day is the key to winning them. They don't start their day in a dashboard. They start it in their IDE.

8:30 AM
Open VS Code. Pull latest. Check GitHub notifications.
9:00 AM
PR review. See a flagged comment about a performance regression in prod.
9:15 AM
Open Datadog or Sentry. Find the trace. Correlate with the deploy from yesterday.
9:30 AM
Suspect it's tied to a feature flag rolled out to 10% last week. Check LaunchDarkly. No direct correlation view. Manual cross-reference.
10:00 AM
Write the flag rollback. Deploy. Incident resolved.
10:30 AM
Sprint planning. PM wants an experiment on the new onboarding flow. Open Statsig. Configure. Write the SDK call. Ship behind the flag.
1:00 PM
SDK integration issue. LaunchDarkly SDK doesn't support the new React 19 hook pattern. Open a support ticket. Wait.
3:00 PM
AI feature ship. Need to test two prompt configs. Experimentation tool doesn't support non-binary outcomes. Build custom logging layer.
5:00 PM
Weekly metrics review. Data lives in 3 tools. Manually stitch Datadog (latency) + Sentry (errors) + Statsig (experiments).

The core pain: the engineer touches 5+ tools in a single day and manually stitches together context that should be automatic.

Evaluation Criteria

What Engineers Actually Evaluate Tools On

Not what shows up in a G2 review. What gets said in Slack and engineering all-hands.

Weight: Very High

SDK Quality

Does it support my framework? Actively maintained? Adds latency? Can I use it offline/edge? Is the API idiomatic or a Java wrapper?

Weight: High

Time to First Flag

How long from npm install to a flag evaluating in production? Is there a CLI wizard or do I have to configure a web UI first?

Weight: High

Stats Engine Trust

Auto-detect sample ratio mismatch? Support CUPED / variance reduction? Custom metrics or only pre-built? Peer-reviewed methodology?

Weight: Medium–High

Observability Integration

Can I see flag state in Datadog / Sentry? Correlate a flag rollout with a latency spike without switching tools? Emit events to my warehouse?

Weight: Medium

Pricing Transparency

Can I start free? Per seat, per event, or per MAU? What does the bill look like at 1M MAUs?

Weight: Medium

Not Feeling Locked In

Public API for my data? Programmatic export of flags and experiments? Will my data be locked in OpenAI's platform? (the Statsig question)

Emerging Segment

The AI Engineer's Emerging Needs

The fastest-growing segment of the engineering persona has needs that almost no tool fully serves today. This is a greenfield opportunity.

  • 1
    Prompt Versioning & A/B Testing
    Ship prompt A vs. prompt B to 50/50 of users, measure quality score, cost per token, and latency simultaneously.
  • 2
    Model Config Management
    Toggle between GPT-4o and Claude at the flag level without a deploy.
  • 3
    Agent Behavior Flags
    Control which tools an agent can call, what its system prompt is, and at what confidence threshold it escalates to human.
  • 4
    Non-Binary Experiment Metrics
    Traditional A/B tests measure clicks and conversions. AI experiments measure qualitative quality, cost, and latency — requiring different statistical approaches.
  • 5
    Synthetic User Testing
    Run experiments against AI-simulated user personas before rolling out to real traffic. Validate experiment design before a single real user sees it.

Anti-Patterns

What the Engineer Persona Is NOT

To avoid building the wrong things, be clear about boundaries:

They are not the DevOps/SRE engineer. That persona owns pipeline health and incident response. They live in Datadog. The product engineer wants a flag and experiment tool that integrates with Datadog, not one that pretends to be Datadog.

They are not PM-adjacent. They don't want a "no-code experiment builder." They want a great API and good CLI.

They are not data scientists. They don't want to configure Bayesian priors. They want a stats engine that "just works" and tells them when to call.

They are not the buyer. They're the champion and user. The buyer is an Engineering Director or VP Eng. But the champion's recommendation carries enormous weight.

They are not loyal to dashboards. They live in their IDE and terminal. Any tool that requires a web UI for core tasks will lose them.
